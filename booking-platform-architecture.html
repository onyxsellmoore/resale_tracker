1Design Philosophy: Three Pillars

Every architectural decision in this platform is rooted in three non-negotiable principles:

🛡️ Reliability First

Double-booking is the cardinal sin of any appointment system. A client cannot be in two places at once, and a staff member cannot serve two clients simultaneously. All architectural decisions, from database transactions to idempotency keys, exist to prevent this failure.

Reliability also means: Timezone correctness — every moment in time is stored as UTC; business timezone is metadata only. Idempotency — clients may retry requests; system gracefully handles duplicate bookings. Zero silent failures — notifications always send, conflicts are always detected, no exceptions are swallowed.

⚡ Ruthless Simplicity

Fight premature abstraction. The entire system runs as a modular monolith — one backend JAR, one database. A new developer runs one command and has a local environment. There are no microservice boundaries to cross, no message queues to debug, no eventual consistency to reconcile.

Solve today's problem. Refactor into services only when the codebase reaches critical mass. Prefer embedded documents in MongoDB over normalized schemas. Prefer direct database transactions over distributed transactions.

✅ Test-Driven Always

No code ships without tests written first. This document itself enforces TDD: every section describes what must be tested. A developer cannot implement double-booking prevention without writing tests for conflict detection first.

Tests are the specification. Tests are the documentation. When in doubt about system behavior, read the tests.

2Tech Stack & Technology Decisions

Backend: Quarkus 3 / Java 21

We use Quarkus instead of Spring Boot for one critical reason: cold start performance. In cloud environments like Google Cloud Run, every deployment creates new instances. Spring Boot's cold start on the JVM is 3–6 seconds; Quarkus with native compilation achieves ~50ms. For a bootstrapping startup, this difference is enormous — it means users wait seconds for their first click.

Spring Boot (JVM)

  • Cold start: 3–6s
  • Memory baseline: ~300MB
  • Warm request: ~50ms
  • Mature ecosystem

Quarkus (Native)

  • Cold start: ~50ms
  • Memory baseline: ~50MB
  • Warm request: ~5ms
  • Same annotations, same ecosystem

Java 21 is chosen for its latest LTS status, virtual threads for high-concurrency I/O, and improved pattern matching. Virtual threads mean our thread pool for handling concurrent booking requests is essentially unlimited — a thread per connection, not a bounded pool.

Why not Node.js or Go?

Node.js has poor type safety and no compile-time checking for data modeling errors. Go compiles to a single binary, but lacks the ecosystem maturity for payments, email, and auth integrations. Java's ecosystem (Hibernate, Quarkus Data, libraries for payment processors) is unmatched. Java 21 + Quarkus closes the performance gap.

Database: MongoDB

We use MongoDB over a relational database (PostgreSQL) for one key reason: document shape varies by business type. A hair salon's service attributes differ from a yoga studio's. A massage therapist cares about client contraindications; a gym cares about membership tier. Relational schemas require migrations and upfront schema design. MongoDB's flexible schema means we ship features without database migrations.

PostgreSQL (Relational)

  • Schema-first (migrations required)
  • Strict ACID, but multi-document ACID is expensive
  • Proven, mature
  • Normalized schema requires many JOINs

MongoDB (Document)

  • Flexible schema (no migrations)
  • Multi-document ACID (4.0+)
  • Embedding related data (service attributes, appointment details)
  • Range queries for conflict detection

MongoDB's multi-document transactions (ACID since version 4.0) mean we can atomically check for conflicts and create an appointment in a single transaction. No race conditions.

Frontend: React + TypeScript

React for component composition and reactivity. TypeScript to catch type errors at compile time before they reach production. The frontend is responsible for:

  • Displaying available time slots (computed by the backend)
  • Client-side timezone handling (display times in the client's local timezone)
  • Appointment booking form with optimistic updates
  • Cancellation and rescheduling workflows

Cloud: Google Cloud Platform (Cloud Run + MongoDB Atlas)

We target GCP Cloud Run because Quarkus's fast startup and low memory footprint are perfect for serverless. The backend starts in ~50ms and autoscales from zero to thousands of instances. MongoDB is hosted on MongoDB Atlas, a managed service with automated backups, sharding, and replica sets.

Zero-friction migration path

The same code runs on a developer's laptop, on a single VM, or on Cloud Run. There is no code change between self-hosted and cloud. Only configuration changes: database connection string, auth provider, email service.

5. appointments (Most Critical)

The heart of the system. Every field is carefully chosen to enforce correctness and enable reliable conflict detection. The version field implements optimistic locking for concurrent updates.

  • id String (ObjectId)
  • businessId String (ObjectId)
  • clientId String (ObjectId)
  • serviceId String (ObjectId)
  • staffId String (ObjectId)
  • startTime Instant (UTC) Appointment start, ALWAYS UTC. E.g., 2026-03-15T18:00:00Z (which is 10am PST if timezone is America/Los_Angeles)
  • endTime Instant (UTC) Service end time PLUS buffer. Used for conflict detection and staff availability.
  • serviceEndTime Instant (UTC) Actual service end time (startTime + serviceDurationMinutes). Without buffer. Used for reminders and no-show detection.
  • status Enum PENDING, CONFIRMED, CANCELLED, NO_SHOW, COMPLETED
  • source Enum ONLINE (client booked), MANUAL (staff created), PHONE (staff booked via call)
  • paymentStatus Enum UNPAID, PAID, REFUNDED. Null if unpaid to avoid null-vs-enum confusion.
  • reminders Array of embedded objects Each: {hoursBeforeAppointment, sentAt (Instant or null), method (EMAIL)}. Tracks which reminders have been sent.
  • version Long Optimistic locking counter. Incremented on every update. Prevents concurrent edit conflicts.
  • clientIdempotencyKey String (UUID) Client provides this on creation. If same key is submitted twice, system returns same appointment (idempotency).
  • createdAt Instant (UTC)
  • updatedAt Instant (UTC)

Three time fields — why?

startTime + endTime define the appointment "block" (includes buffer). Used for conflict detection. If a 60-minute massage with 15-minute buffer occupies 3pm–3:15pm, the staff member is unavailable for that entire period.

serviceEndTime is the actual service end (startTime + serviceDurationMinutes, no buffer). Used for reminder jobs and no-show detection logic.

4Critical Reliability Patterns

Double-Booking Prevention (The Most Important Section)

Double-booking is the cardinal sin. A client must not be assigned two appointments at the same time. A staff member must not be assigned two clients simultaneously. The system prevents this with three layers of defense:

Layer 1: Range Overlap Query + Transaction

When a client attempts to book a service with a specific staff member at a specific time, the system:

  1. Checks for conflicts with a database query that finds all appointments where:
    • businessId equals the client's business
    • staffId equals the requested staff member
    • status is PENDING or CONFIRMED (excludes CANCELLED, NO_SHOW, COMPLETED)
    • startTime < requestedEndTime AND endTime > requestedStartTime (time range overlap)
  2. If conflicts exist, returns error: "Staff member unavailable at this time"
  3. If no conflicts, wraps the conflict-check and appointment-insert in a MongoDB multi-document transaction. This is atomic: either both succeed or both fail. No race condition between check and insert.

Why not a unique index?

A naive approach is a unique index on (businessId, staffId, startTime). This fails because:
1. Two appointments at different times (10am–11am, 11am–12pm) must both exist.
2. A unique index cannot express a time-range constraint.
3. You need range overlap detection, which requires the query above.

Layer 2: Optimistic Locking

The version field on every appointment is a Long counter. When any update occurs (status change, cancellation), the update query includes a check: version == expectedVersion. If another thread has changed the appointment since we read it, the query returns 0 affected documents, signaling a conflict.

This is a second line of defense. A client cannot accidentally confirm an appointment that a staff member just cancelled. 

// Pseudo-code for status update
db.appointments.updateOne(
  {
    _id: appointmentId,
    businessId: businessId,
    version: currentVersion  // <-- Optimistic lock check
  },
  {
    $set: {
      status: newStatus,
      version: currentVersion + 1
    }
  }
);

Layer 3: Idempotent Booking Creation

Clients may retry booking requests due to network timeouts. The system must not create duplicate appointments. Every booking request includes a clientIdempotencyKey (a UUID provided by the client or generated on the frontend).

Before creating an appointment, the system queries: db.appointments.findOne({clientIdempotencyKey, status: {$ne: 'CANCELLED'}}). If found, return that appointment. If not found, create one with this key. This guarantees that retrying the same request returns the same appointment.

Three-layer defense

Transaction + range query prevents races. Optimistic locking catches concurrent updates. Idempotency keys handle client retries. Together, double-booking becomes impossible.

Timezone Handling

Critical: Timezones are complex

Every moment in time is stored as UTC Instant. Business timezone is stored only as metadata (IANA identifier, e.g., "America/New_York"). Display and interpretation always uses ZoneId to account for daylight saving time.

Rule: Always store as UTC

Appointment startTime and endTime are ALWAYS UTC Instant. A client in San Francisco and a staff member in New York must see the same appointment time in UTC, even though their local clocks differ.

Rule: Staff schedules defined in local time

A salon's weekly schedule says "open 9am–6pm Monday–Friday". This is in the salon's local time. When computing available slots for a date, the system:

  1. Loads the business's timezone (e.g., "America/Los_Angeles")
  2. Gets the staff's weekly schedule (e.g., "09:00–18:00 on Monday")
  3. Converts local time to UTC using ZoneId (accounts for DST)
  4. Queries appointments in UTC range
  5. Returns available slots in UTC
  6. Frontend converts UTC to client's local timezone for display

Rule: Never use raw offsets

Incorrect: using "+08:00" as a timezone. Correct: using "Asia/Singapore". Raw offsets don't account for daylight saving time transitions. A US Eastern timezone changes from EST (−5) to EDT (−4) on the second Sunday in March. Using a hard offset breaks on that day. 

// Correct: ZoneId accounts for DST
ZoneId businessZone = ZoneId.of("America/New_York");
LocalDateTime localStartTime = LocalDateTime.of(2026, 3, 20, 14, 0);
ZonedDateTime zonedTime = localStartTime.atZone(businessZone);
Instant utcTime = zonedTime.toInstant();
// utcTime is correct, even if DST transition occurs

// Incorrect: raw offset ignores DST
ZoneOffset offset = ZoneOffset.of("-05:00");
Instant wrongTime = localStartTime.toInstant(offset);
// If DST changed between stored offset and actual date, wrongTime is wrong

Idempotency and Retries

Network requests may fail. Clients retry. The system must handle retries gracefully without creating duplicates.

Every booking request must include a unique clientIdempotencyKey (string UUID). The system stores this key on the appointment. If the same request arrives twice:

  1. First request creates appointment with key = UUID
  2. Second request queries for existing appointment with same key
  3. Found, returns existing appointment (no new duplicate created)

Idempotency must also apply to status transitions. Marking an appointment as COMPLETED twice should be safe. The second update simply confirms what's already set.

No Silent Failures

Every failure is logged and surfaced. Example: a reminder email fails to send. The system:

  1. Logs the failure with context (which appointment, which reminder, why email failed)
  2. Retries the email (exponential backoff, max 3 attempts)
  3. If still failing, marks the reminder with failureReason and alerts the business owner

Business owners must never discover a client missed a reminder because an email silently failed to send. The system is observable and alarming.

5Key Services & Business Logic

1. BookingService

Orchestrates appointment creation. Enforces double-booking prevention, idempotency, and status transitions.

Methods:

  • createAppointment(CreateAppointmentRequest) — Accepts service, staff, date+time. Checks conflicts in a transaction. Returns appointment or error.
  • updateAppointmentStatus(appointmentId, newStatus, version) — Uses optimistic locking. Validates status transition. Updates client stats.
  • cancelAppointment(appointmentId, reason) — Sets status to CANCELLED. Frees slot. Notifies client and staff.
  • rescheduleAppointment(appointmentId, newTime) — Checks new time for conflicts. Atomically updates appointment. Notifies parties.

Test-Driven: What must be tested

✓ Creating appointment with no conflicts succeeds
✓ Creating appointment with overlapping appointment fails
✓ Creating appointment with same idempotency key twice returns same appointment
✓ Optimistic lock prevents concurrent updates
✓ Cancellation frees the slot for future bookings
✓ Status transitions follow valid lifecycle (PENDING → CONFIRMED → COMPLETED, not COMPLETED → PENDING)

2. AvailabilityService

Computes available time slots for a service on a given date. Accounts for staff working hours, existing appointments, buffer times, and business exceptions.

Methods:

  • getAvailableSlots(businessId, serviceId, staffId, dateInLocalTime, durationMinutes) — Returns list of available start times (in UTC). Frontend converts to client's local timezone.
  • isSlotAvailable(businessId, serviceId, staffId, startTimeUTC, endTimeUTC) — Boolean check for a specific slot.

Algorithm for getAvailableSlots:

  1. Load business (get timezone), service (get durationMinutes, bufferMinutes), and staff (get weeklySchedule)
  2. Convert local date to UTC date range (00:00–23:59 in business timezone)
  3. Get staff's working hours for that day (from weeklySchedule, or null if day off, or override from exceptions)
  4. Convert working hours from local to UTC
  5. Query all appointments for that staff on that date (status PENDING or CONFIRMED)
  6. Build list of available 15-minute or 30-minute slots, skipping occupied times and buffers
  7. Return in UTC

Test-Driven: What must be tested

✓ Staff's working hours are correctly converted from local to UTC
✓ DST transitions are handled (spring forward, fall back)
✓ Existing appointments block slots (including buffers)
✓ Days with exceptions (holidays) are unavailable
✓ Days with modified hours (e.g., 10am–2pm) are respected
✓ Available slots do not overlap with existing appointments + buffers

3. AppointmentService

CRUD operations and lifecycle management. Handles queries, status changes, and data consistency.

Methods:

  • getAppointment(id) — Fetch by ID
  • listAppointmentsByBusiness(businessId, filters) — Query with optional date range, status, staff, client
  • listAppointmentsByClient(clientId) — Client's booking history
  • completeAppointment(appointmentId) — Mark as COMPLETED, update client stats

4. ClientService

Manage client profiles and statistics.

Methods:

  • createClient(firstName, lastName, email, phone) — New client profile
  • updateClient(id, updates) — Modify name, email, notes
  • getClientStats(clientId) — Return stats object (total appointments, no-shows, cancellations, last visit)

5. NotificationService

Sends emails for confirmations, reminders, and cancellations. Must be reliable and observable.

Methods:

  • sendConfirmationEmail(appointmentId) — Sent immediately after booking confirmed
  • sendReminderEmail(appointmentId, hoursBeforeAppointment) — Sent by scheduled job
  • sendCancellationEmail(appointmentId, reason) — Sent when appointment cancelled

Each method is idempotent: sending the same email twice is safe (checks if reminder already sent before marking as sent).

6. ReportingService

Business analytics. Helps owners understand performance.

Methods:

  • getRevenueByPeriod(businessId, startDate, endDate) — Total revenue from COMPLETED appointments
  • getPopularServices(businessId, limit) — Services with most bookings
  • getNoShowRate(businessId, startDate, endDate) — Percentage of appointments marked NO_SHOW
  • getClientRetention(businessId) — Repeat clients vs one-time visitors

State Definitions

Status Meaning Valid Transitions Automatic Triggers
PENDING Appointment created, awaiting confirmation (if autoConfirm=false) → CONFIRMED, → CANCELLED None
CONFIRMED Appointment confirmed, client expects to arrive → COMPLETED, → CANCELLED, → NO_SHOW Automatic confirmation if businessSetting autoConfirm=true

CANCELLED Appointment cancelled (by client or staff) None (terminal) Client or staff initiates cancellation
NO_SHOW Client did not arrive for confirmed appointment None (terminal) Automatic detection: 15 min past serviceEndTime with no COMPLETED status

7Key Data Flows

Flow A: Client Books Online

Client Self-Service Booking

  1. Client selects service (e.g., "Deep Tissue Massage")
  2. Client selects preferred staff member (or "next available")
  3. Frontend calls getAvailableSlots(serviceId, staffId, dateInLocalTime)
  4. Backend returns list of available times in UTC, frontend converts to client's local time
  5. Client selects a slot (e.g., "Friday, March 20, 3:00 PM")
  6. Client submits booking with clientIdempotencyKey = UUID()
  7. Backend checks for conflicts in a transaction (layer 1 defense)
  8. Backend creates appointment with status PENDING (or CONFIRMED if autoConfirm=true)
  9. NotificationService sends confirmation email to client and staff
  10. Frontend shows "Booking confirmed. You'll receive a reminder 24 hours before."

Flow B: Business Creates Manual Booking

Staff Books on Behalf of Client

  1. Staff selects client (existing or creates new)
  2. Staff selects service and staff member (often themselves)
  3. Staff selects date and time (or calls getAvailableSlots)
  4. Staff submits booking
  5. Backend checks for conflicts, creates appointment with status CONFIRMED (no pending step)
  6. NotificationService sends confirmation email to client and staff

Flow C: Reminder Job (Scheduled)

Automated Reminder Emails

  1. Scheduled job runs hourly (e.g., every hour at :00 minutes)
  2. Queries appointments where status = CONFIRMED and reminders contain unsent reminder
  3. For each appointment with a reminder due:
    1. Calculate: is it within 2 hours of the next scheduled reminder window? (e.g., is it within 2 hours of the 24-hour-before mark?)
    2. If yes and reminder not yet sent: call NotificationService.sendReminderEmail(appointmentId, hoursBeforeAppointment)
    3. Update appointment.reminders[i].sentAt = now()
  4. Log any failures; alert business owner if retries exhausted

Flow D: Cancellation

Client or Staff Cancels Appointment

  1. Client or staff initiates cancellation (via UI or API)
  2. Backend calls cancelAppointment(appointmentId, reason)
  3. Updates appointment status to CANCELLED
  4. Slot is immediately freed (next availability check will show this time as available)
  5. NotificationService sends cancellation email to both parties
  6. ClientService updates client stats (increments cancelledCount)
  7. Business rule: cancellation within cancellationHoursNotice of appointment may incur fee (stored in appointment, not enforced here)

Flow E: No-Show Detection

Automatic No-Show Marking

  1. Scheduled job runs every 15 minutes
  2. Queries appointments where status = CONFIRMED and now() > serviceEndTime + 15 minutes
  3. For each appointment: update status to NO_SHOW
  4. ClientService increments client.stats.noShowCount
  5. Optional: NotificationService sends alert to business owner ("Client Alice Thompson no-showed for 3pm appointment")

9System Automation & Smart Defaults

The system automates common workflows so business owners don't manually handle them.

What Runs Automatically

Automation Trigger Action
Confirmation Email Appointment created with status CONFIRMED Send email to client and staff with details, reminder times
Reminder Emails (24h, 2h before) Scheduled job runs hourly; checks if reminder is due Send reminder email; mark reminder as sent
No-Show Detection Scheduled job runs every 15 min; checks appointments past serviceEndTime + 15 min Mark status as NO_SHOW; increment client stats; optionally alert owner
Client Stats Updates Appointment status changes (to COMPLETED, CANCELLED, NO_SHOW) Increment relevant counter (totalAppointments, cancelledCount, noShowCount); update lastVisitAt
Staff Availability Blocking Availability slot calculation Exclude times during staff exceptions (holidays, modified hours)
Auto-Confirmation Appointment created; bookingSettings.autoConfirm = true Immediately set status to CONFIRMED (no PENDING step)

Configurable Defaults by Business

In the businesses.bookingSettings document:

  • advanceBookingDays — How far in advance clients can book (e.g., 60 = only see slots up to 60 days ahead)
  • cancellationHoursNotice — Minimum hours notice required to cancel without penalty (e.g., 24 = must cancel 24 hours ahead)
  • autoConfirm — If true, appointments are immediately CONFIRMED; if false, they remain PENDING until staff confirms
  • reminderHoursBefore — Array of hours to send reminders (e.g., [24, 2] = send 24 hours and 2 hours before)

10Testing Strategy

No code ships without tests written first. Every section of this architecture document implies test cases. Here's the strategy:

Unit Tests (Domain Logic)

Test individual services in isolation, mocking the database.

  • BookingService
    • Test conflict detection: overlapping appointments are rejected
    • Test idempotency: same request twice returns same appointment
    • Test optimistic locking: concurrent updates are rejected
    • Test status transitions: PENDING → CONFIRMED → COMPLETED is valid; COMPLETED → PENDING is invalid
  • AvailabilityService
    • Test timezone conversion: local time → UTC is correct for given IANA timezone
    • Test DST transitions: spring forward and fall back are handled
    • Test slot blocking: existing appointments + buffers exclude future slots
    • Test exceptions: staff day off (exception with no hours) returns no slots
  • ClientService
    • Test stats update: appointment completion increments totalAppointments and updates lastVisitAt
    • Test no-show detection: incrementing noShowCount works

Integration Tests (Database + Services)

Test services with a real MongoDB instance (in a Docker container during test runs).

  • Test multi-document transaction: conflict check + insert is atomic
  • Test appointment creation end-to-end: all side effects occur (notification queued, client stats updated)
  • Test concurrent bookings: two threads booking same slot, only one succeeds

API Integration Tests

Test REST endpoints with a real (or test) database.

  • Test POST /appointments: create, get conflict response, test idempotency
  • Test GET /appointments/:id/available-slots: returns available times in UTC
  • Test PATCH /appointments/:id: status update, optimistic locking
  • Test POST /appointments/:id/cancel: cancellation flow

End-to-End Tests

Test entire flows: client books, receives confirmation email, receives 2-hour reminder, appointment occurs.

  • Mock email service to capture sent emails
  • Mock scheduled jobs (advance time in test clock)
  • Verify email contains correct appointment details and timezone-aware display times

Test Data & Fixtures

Use factories to create consistent test data:

  • BusinessFactory — creates a test business with default settings
  • ServiceFactory — creates a test service (60 min, 15 min buffer, $100)
  • StaffFactory — creates staff with default 9am–5pm schedule
  • ClientFactory — creates a test client
  • AppointmentFactory — creates an appointment with sensible defaults

Coverage Goals

Aim for 80%+ line coverage on critical paths (BookingService, AvailabilityService, AppointmentService). Lower tolerance for NotificationService (email mocking reduces coverage value).

Test-driven discipline

Write tests before implementation. Tests are the specification. If a developer is unsure how double-booking prevention should work, they read the test. This eliminates ambiguity.

Conclusion

This architecture is built on three pillars: reliability first, ruthless simplicity, and test-driven always. Every decision — from MongoDB over relational databases, to Quarkus over Spring Boot, to multi-document transactions, to storing times as UTC — serves these principles.

The system is small enough for a single developer to understand and modify. It's scalable from a laptop to millions of appointments. It handles edge cases (timezones, DST, idempotency, concurrent bookings) correctly. And it's thoroughly tested from the start.

For a bootstrapping startup building a booking platform, this architecture eliminates false choices: simplicity is not sacrificed for correctness. Reliability is not achieved at the cost of complexity. Speed to market is not compromised by premature optimization.
