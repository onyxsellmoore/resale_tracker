Utility Prompt

Generate CONTEXT.md

One-shot prompt that scans the codebase and produces a permanent, token-efficient architecture reference that every future Claude Code session reads first.

Why This Matters

⚡
Faster sessions

Claude reads one 300-line file instead of scanning 80+ source files on every task.

🎯
Accurate edits

Correct file paths, class names, and patterns on the first try — no hallucinated structure.

💬
Lower token cost

A tight context document uses a fraction of the tokens that a full project scan costs.

🔄
Self-updating

Re-run this prompt after any sprint to keep CONTEXT.md current with the latest architecture.

What CONTEXT.md Will Contain

  • Project Purpose 3 sentences max
  • Tech Stack one line per layer
  • Domain Model entities + key fields
  • Role Permission Matrix compact table
  • API Endpoints method · path · purpose · roles
  • Frontend Routes path · component · guards
  • Key File Map 20–30 files, one sentence each
  • Engineering Rules non-negotiable constraints
  • Common Patterns copy-paste code templates
  • Running the App exact commands
  • Environment Variables all required vars + purpose

Generate project CONTEXT.md

Prompt
You are working in the inventory and sales ledger project.
Your job is to generate a single CONTEXT.md file at the project root.
This file will be read at the start of every future Claude Code session
instead of scanning the whole codebase. Accuracy is critical — read the
actual source files before writing anything.

════════════════════════════════════════════════════════
STEP 1 — Map the project structure
════════════════════════════════════════════════════════
Run these commands and review the output before writing a single line:

  # Backend source tree
  find src/main/java -type f -name "*.java" | sort

  # Frontend source tree
  find frontend/src -type f \( -name "*.tsx" -o -name "*.ts" \) \
    | grep -v node_modules | grep -v dist | sort

  # Config and infra files
  ls -1 *.yml *.yaml *.env* docker-compose* CLAUDE.md 2>/dev/null
  cat src/main/resources/application.properties
  cat frontend/package.json | python3 -m json.tool | grep -A 30 '"scripts"'

Then read every file in these directories completely:
  src/main/java/**/domain/         (entities and enums)
  src/main/java/**/repository/     (data access)
  src/main/java/**/resource/       (REST endpoints)
  frontend/src/context/            (auth + global state)
  frontend/src/api/                (API client functions)
  frontend/src/pages/              (all page components)
  frontend/src/App.tsx             (routing declaration)
  frontend/src/theme.css           (design tokens)
  frontend/playwright.config.ts    (if it exists)
  docker-compose.yml
  CLAUDE.md

════════════════════════════════════════════════════════
STEP 2 — Write CONTEXT.md
════════════════════════════════════════════════════════
Generate the file with the sections below. Rules that apply to every section:
  - No introductory sentences. Start each section with content, not preamble.
  - Prefer tables, code blocks, and bullet lists over prose.
  - Use real names, paths, and values from the actual code you read.
    Never invent a class name, file path, or field that does not exist.
  - Optimise for Claude Code reading speed: consistent indentation,
    aligned columns, and grep-friendly prefixes (BACKEND:, FRONTEND:, etc.)

─── § 1  Project Purpose ─────────────────────────────────────────────────
Three sentences:
  1. What the app does and for whom.
  2. What "booking" means in this context (bookkeeping, not scheduling).
  3. Deployment target.

─── § 2  Tech Stack ──────────────────────────────────────────────────────
One line per layer, format: Layer: value
  Backend / Database / Money type / Frontend / Build tool /
  Auth / Local dev / E2E tests / CI

─── § 3  Domain Model ────────────────────────────────────────────────────
For each MongoDB entity, one block:
  EntityName  (collection: "collection_name")
    field_name  Type       — purpose
    ...
  Mark computed fields with (computed).
  Include only fields that are needed to understand the data shape.
  Do NOT include every field — omit implementation details like createdAt
  unless they are referenced from other entities.

─── § 4  Role Permission Matrix ──────────────────────────────────────────
Compact ASCII table. Rows = endpoint patterns, Columns = roles.
  ✓ = allowed   – = forbidden
  Example row: POST /api/items        ✓   ✓   –   –

─── § 5  API Endpoints ───────────────────────────────────────────────────
One line per endpoint:
  METHOD  /path                — short purpose          [ROLE,ROLE]
Group by resource. Mark public endpoints (no JWT required) with [PUBLIC].

─── § 6  Frontend Routes ─────────────────────────────────────────────────
One line per route:
  /path          ComponentFile.tsx    [PUBLIC | roles]
Mark the default redirect for unauthenticated users.
Mark the post-login landing page.

─── § 7  Key File Map ────────────────────────────────────────────────────
The 25 most important files. Format:
  BACKEND:  path/to/File.java         — one sentence
  FRONTEND: path/to/file.tsx          — one sentence
  INFRA:    filename                  — one sentence
Group: BACKEND DOMAIN / BACKEND API / FRONTEND PAGES /
       FRONTEND COMPONENTS / FRONTEND STATE / TESTS / INFRA

─── § 8  Engineering Rules ───────────────────────────────────────────────
Bullet list. Derive from CLAUDE.md plus any invariants you see enforced
in the source code. Include at minimum:
  - TDD rule
  - Money type rule (no float/double)
  - Security rule (orgId source)
  - Auth rule (every endpoint must have @RolesAllowed)
  - CSS rule (no hardcoded hex values)
  - Test hygiene rule

─── § 9  Common Patterns ─────────────────────────────────────────────────
Five minimal templates. Each is a skeleton — just enough to show the
pattern, not a full implementation. Label each clearly.

  PATTERN A — New REST endpoint (Quarkus)
    Show: class annotation, method signature, @RolesAllowed, orgId extraction,
          response type. 15 lines max.

  PATTERN B — New React page
    Show: file location convention, useQuery call with auth header,
          ProtectedRoute registration in App.tsx. 15 lines max.

  PATTERN C — New API function (frontend)
    Show: file location, auth header injection, error handling shape.
    10 lines max.

  PATTERN D — Backend integration test
    Show: class annotation (@QuarkusIntegrationTest), how to generate a
          test JWT with a specific role, how to call an endpoint and assert
          status code. 15 lines max.

  PATTERN E — Frontend unit test (Vitest + Testing Library)
    Show: render call, mock for useAuth, API mock, and one assertion.
    15 lines max.

─── § 10  Running the App ────────────────────────────────────────────────
Three subsections with exact copy-paste commands:
  Start full stack locally
  Run all tests (backend → frontend unit → E2E, in order)
  Rebuild after dependency changes

─── § 11  Environment Variables ──────────────────────────────────────────
Table: Variable | Purpose | Set in
Include all required variables. Flag any that must be changed before
production deployment.

════════════════════════════════════════════════════════
STEP 3 — Length check and trim
════════════════════════════════════════════════════════
Count the lines in the draft CONTEXT.md:
  wc -l CONTEXT.md

Target: ≤ 350 lines.   Hard limit: 500 lines.

If over the hard limit, trim in this order until under 500:
  1. Remove any prose sentences from sections 1-8. Tables and bullets only.
  2. Cut PATTERN D and PATTERN E to 8 lines each.
  3. In § 7 Key File Map, keep only the 20 most critical files.
  4. In § 5 API Endpoints, merge endpoint variants (GET /id + GET /) to one line.

Do NOT trim § 4 (permission matrix) or § 8 (engineering rules) — these are
the most valuable sections for preventing mistakes.

════════════════════════════════════════════════════════
STEP 4 — Write the file and update CLAUDE.md
════════════════════════════════════════════════════════
1. Write the trimmed document to CONTEXT.md at the project root
   (same directory as docker-compose.yml and CLAUDE.md).

2. Open CLAUDE.md and append this line at the top (before existing content):
     Read CONTEXT.md before making any changes.

3. Print the final line count:
     wc -l CONTEXT.md

4. Print a one-line summary of each section and its line count so it is
   easy to see where the bulk of the document lives.

════════════════════════════════════════════════════════
CONSTRAINTS
════════════════════════════════════════════════════════
- Read before you write. Every class name, file path, and field name in
  CONTEXT.md must exist in the actual codebase as of this run.
- CONTEXT.md is a living document. It should be re-generated after
  every sprint by running this prompt again. It can be committed to git.
- The document is for Claude Code, not for humans. Write for a machine
  reader: consistent markers, no filler words, aligned columns.
- Do not add CONTEXT.md to .gitignore. Commit it with the repo.
When to re-run this prompt: after completing any sprint that adds new entities, endpoints, pages, or changes the permission model. Running it takes ~2 minutes and keeps every future session accurate from the first message. Add a reminder comment at the top of each future implementation plan: Read CONTEXT.md before starting.
