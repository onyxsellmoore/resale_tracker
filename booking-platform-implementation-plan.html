ENTITY 1 — Item
Represents a physical product the owner has purchased for resale.

Fields:
  id (ObjectId), businessId (String, indexed),
  name (String, required), brand (String), category (String),
  condition (enum: EXCELLENT / GOOD / FAIR / POOR),
  purchasePrice (Decimal128, required, >= 0),
  purchaseDate (Instant, required),
  description (String), notes (String),
  status (enum: AVAILABLE / SOLD, default AVAILABLE),
  createdAt (Instant), updatedAt (Instant)

ENTITY 2 — Sale
Represents a completed sale — the act of "booking" a sale in the ledger.
Created when an Item is sold. Immutable after creation.

Fields:
  id (ObjectId), businessId (String, indexed),
  itemId (String, required — must reference an Item),
  platform (String, required — e.g. "Poshmark", "Vestiaire", "Mercari"),
  salePrice (Decimal128, required, > 0),
  platformFees (Decimal128, required, >= 0),
  netProceeds (Decimal128 — computed: salePrice - platformFees),
  profit (Decimal128 — computed: netProceeds - item.purchasePrice),
  soldAt (Instant, required),
  notes (String),
  createdAt (Instant)

Note: netProceeds and profit are computed at write time and stored.
Do not recompute them on read — purchasePrice may be corrected later
and stored profit must reflect what was recorded at the time of sale.

INDEXES:
  Item:  { businessId: 1, status: 1 }
  Item:  { businessId: 1, brand: 1 }
  Sale:  { businessId: 1, soldAt: -1 }
  Sale:  { businessId: 1, itemId: 1 }

DECIMAL128 CODEC: Register a MongoClientCustomizer bean that
configures Decimal128 codec for BigDecimal fields. Verify with
a MoneyTest: $12.50 stored and retrieved without precision loss.

WRITE TESTS FIRST, then implement:

SaleRepositoryTest:
  a. save and findById — sale round-trips with correct computed fields

  c. findBySoldAtRange — date range filter works

MoneyTest:

  Soft-delete: sets status = DELETED (add DELETED to the enum).
  Only allowed if status = AVAILABLE. A sold item is in the ledger

6. GET by id correct businessId → 200.
7. GET by id wrong businessId → 404.
8. PATCH updates name and condition; purchasePrice unchanged.
9. DELETE AVAILABLE item → 204; item no longer appears in list.
10. DELETE SOLD item → 409 (sold items are permanent ledger entries).

Sales Recording API — "Book a Sale"

Sprint 1 REST Ledger
Copy-paste prompt
Continue. All existing tests must remain green.

TASK: Sales recording API — the act of booking a sale in the ledger.
Write tests first.

ENDPOINTS — write SaleResourceTest before SaleResource:

POST /api/v1/sales
  Body: { businessId, itemId, platform, salePrice,
          platformFees, soldAt, notes }
  This is the primary write operation. On success:
    1. Validates item exists, belongs to businessId, and is AVAILABLE.
    2. Computes netProceeds = salePrice - platformFees.
    3. Fetches item.purchasePrice; computes profit = netProceeds - purchasePrice.
    4. Saves the Sale with all computed fields.
    5. Sets item.status = SOLD.
  Returns 201 + SaleDTO (including computed profit and item name).
  This operation is atomic: if the Sale save fails, item stays AVAILABLE.

GET /api/v1/sales?businessId=X
  Returns all sales for the business, newest first (sorted by soldAt).
  Optional filters: platform, from (ISO date), to (ISO date).

GET /api/v1/sales/{id}?businessId=X
  Returns 200 + SaleDTO with embedded item name and brand, or 404.

TEST CASES in SaleResourceTest:
1. POST valid sale → 201; item status becomes SOLD.
2. POST profit computed correctly:
   purchasePrice=$40, salePrice=$100, platformFees=$15
   → netProceeds=$85.00, profit=$45.00 (exact BigDecimal).
3. POST item already SOLD → 409 "Item is already sold".
4. POST itemId not found → 404.
5. POST itemId belonging to different businessId → 404.
6. POST salePrice = 0 → 400.
7. POST platformFees > salePrice → 400
   (fees cannot exceed sale price).
8. GET list → newest sale appears first.
9. GET list with platform filter → only matching platform returned.
10. GET by id → 200 with item name embedded.
11. GET by id wrong businessId → 404.

Run ./mvnw test. All green before finishing.

Definition of Done

  • All 11 sales tests pass
  • Profit arithmetic test passes with exact BigDecimal values (no rounding)
  • Double-sale prevented: SOLD item returns 409 (tested)
  • Cross-business item access returns 404 (tested)
  • Item status atomically updated to SOLD on sale creation
  • ./mvnw test exits 0

ADD DEPENDENCY: quarkus-smallrye-jwt.

ONE OWNER PER BUSINESS. No roles. Keep it simple.

ENDPOINTS:
POST /api/v1/auth/login
  Body: { email, password }
  Returns: { accessToken (JWT, 15 min), refreshToken (opaque, 7d) }
  JWT claims: { sub: ownerId, businessId }

POST /api/v1/auth/refresh
  Body: { refreshToken }
  Returns: { accessToken }

POST /api/v1/auth/logout
  Body: { refreshToken }
  Marks the token used in MongoDB so it cannot be reused.

PROTECTION:
All /api/v1/** routes require a valid JWT, EXCEPT:
  POST /api/v1/auth/login
  POST /api/v1/auth/refresh
The businessId claim in the JWT must match the businessId in every
request body or query param — mismatch returns 403.

WRITE AuthResourceTest and SecurityFilterTest FIRST.

TEST CASES — AuthResourceTest:
1. login_valid → 200 with both tokens.
2. login_wrongPassword → 401.
3. login_unknownEmail → 401 with identical response to wrong
   password (no user enumeration).
4. refresh_valid → 200 with new accessToken.
5. refresh_expired → 401.
6. logout_thenRefresh → 401 after logout.

TEST CASES — SecurityFilterTest:
7. inventoryRoute_noToken → 401.
8. inventoryRoute_validToken_matchingBusiness → 200.
9. inventoryRoute_validToken_wrongBusiness → 403.

PASSWORDS: bcrypt, cost factor 12. Never store plaintext.
REFRESH TOKENS: SHA-256 hash stored in MongoDB with TTL index.
