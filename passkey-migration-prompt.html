Auth Migration

Passkey-Only Authentication

Remove all password auth. Implement WebAuthn passkeys end-to-end, seed a dev test user, and verify every flow.

Before You Touch Any Code

1
Read CONTEXT.md — it is the single source of truth for the stack, domain model, patterns and rules.
2
Follow TDD always: write failing tests first, then implement. One failing test → one implementation → green → next.
3
Simplicity over everything. No new frameworks. Use the browser's native navigator.credentials API (zero extra npm packages). For CBOR parsing on the backend, add only jackson-dataformat-cbor.

Current Bugs / What Is Wrong

BEPOST /api/v1/auth/register requires adminPassword, BCrypt-hashes it, stores passwordHash on User — passkeys are never registered during setup.
BEPOST /api/v1/auth/login is a password endpoint. WebAuthn login endpoints exist (/login/begin, /login/complete) but the UI never calls them.
BENo /register/begin or /register/complete endpoints exist — there is no way for the browser to register a passkey credential.
FELoginPage.tsx shows email + password fields. It calls the password /login endpoint.
FEOrgSetupPage.tsx shows Password + Confirm Password fields. It passes adminPassword to /register.
FEauthApi.ts — RegisterPayload includes adminPassword; LoginPayload includes password. No passkey API functions exist.

// NEW: generate WebAuthn creation options for passkey registration
public Optional<Map<String,Object>> registerBegin(String email) {
  // find user by email → empty if not found
  // generate 32-byte random challenge, store in challenges map (5 min TTL)
  // return creation options map:
  //   challenge, rp:{id:rpId, name:rpName}, user:{id:userId, name:email, displayName},
  //   pubKeyCredParams:[{type:"public-key",alg:-7}], timeout:60000, attestation:"none"
}

// NEW: verify attestation, store credential, issue token pair
public Optional<TokenPair> registerComplete(
    String email, String credentialId,
    String attestationObjectB64, String clientDataJSONB64) {
  // 1. find user by email
  // 2. decode + verify clientDataJSON:
  //    type == "webauthn.create", origin == expectedOrigin, challenge in map + not expired
  // 3. decode attestationObject (CBOR via CBORFactory):
  //    extract authData bytes from map key "authData"
  // 4. parse authData:
  //    bytes 0-31: rpIdHash == SHA-256(rpId)
  //    byte 32: flags — UP (bit 0) must be set
  //    bytes 37-52: AAGUID (16 bytes, ignored)
  //    bytes 53-54: credIdLen (big-endian uint16)
  //    bytes 55..55+credIdLen: credentialId bytes → base64url → must match credentialId param
  //    bytes 55+credIdLen..: COSE key (CBOR map)
  // 5. parse COSE key (CBORFactory): kty(1)==2(EC), alg(3)==-7(ES256), crv(-1)==1(P-256),
  //    x(-2) 32 bytes, y(-3) 32 bytes
  // 6. convert x,y to X.509 SubjectPublicKeyInfo DER (uncompressed point 0x04 prefix,
  //    wrap with EC OID 1.2.840.10045.2.1 + P-256 OID 1.2.840.10045.3.1.7)
  //    → base64url-encode → store as cred.publicKey
  // 7. check no existing credential for this credentialId
  // 8. persist WebAuthnCredential{ownerId, credentialId, publicKey, signCount=0}
  // 9. return generateTokens(user)
}
COSE → X.509 DER tip: the EC public key SubjectPublicKeyInfo DER header bytes for P-256 are the fixed prefix 30 59 30 13 06 07 2a 86 48 ce 3d 02 01 06 08 2a 86 48 ce 3d 03 01 07 03 42 00 04 followed by the 32-byte X and 32-byte Y coordinates (total = 91 bytes). No extra library needed.

2 — OrgSetupPage.tsx

// REMOVE: password, confirmPassword state + fields + validation
// NEW submit flow (replace handleSubmit body):

async function handleSubmit(e) {
  e.preventDefault()
  // 1. validate: orgName, slug, displayName, email only (no password checks)

  // 2. call register() → { orgId, userId, role }  — no token yet
  const regResult = await register({ orgName, orgSlug, adminEmail, adminDisplayName })
  if (!regResult.data) { setErrors([regResult.error]); return }

  // 3. get WebAuthn creation options from server
  const options = await beginPasskeyRegistration(email)

  // 4. browser prompts user to create passkey (Touch ID / Face ID / Windows Hello)
  const credential = await navigator.credentials.create({
    publicKey: {
      ...options,
      challenge: b64urlToBytes(options.challenge),
      user: { ...options.user, id: b64urlToBytes(options.user.id) },
    }
  }) as PublicKeyCredential

  // 5. send attestation to server → get JWT pair
  const auth = await completePasskeyRegistration(email, credential)

  // 6. store token + navigate
  login(auth.accessToken)        // AuthContext.login takes the access token string
  navigate('/analytics', { replace: true })
}
Show a friendly status message between steps 2 and 3: "Organization created! Now set up your passkey…" — so the user knows why the browser is prompting them.

3 — LoginPage.tsx

// REMOVE: password state + field
// The form now has only: email input + "Sign in with passkey" button
// NEW handleSubmit:

async function handleSubmit(e) {
  e.preventDefault()
  if (!email.trim()) return
  setError(null); setSubmitting(true)
  try {
    // 1. get assertion options from server
    const options = await beginPasskeyLogin(email)

    // 2. browser prompts user to authenticate with passkey
    const assertion = await navigator.credentials.get({
      publicKey: {
        ...options,
        challenge: b64urlToBytes(options.rawChallenge),
        allowCredentials: options.allowCredentials?.map(c => ({
          ...c, id: b64urlToBytes(c.id as unknown as string)
        }))
      }
    }) as PublicKeyCredential

    // 3. verify assertion → get JWT pair
    const auth = await completePasskeyLogin(email, assertion)
    login(auth.accessToken)
    navigate('/analytics', { replace: true })
  } catch (err: any) {
    // NotAllowedError = user cancelled; otherwise generic error
    setError(err?.name === 'NotAllowedError'
      ? 'Passkey sign-in was cancelled.'
      : 'Sign-in failed. Make sure you have a passkey registered for this account.')
  } finally { setSubmitting(false) }
}

Seed Test User for Dev / Manual UI Testing

Because passkeys are device-bound, a fully automated seed is not meaningful for manual UI testing — the developer must create their own passkey on their own device. Provide a thin seed script that creates the org+user records, then the developer registers their passkey once through the browser.

scripts/seed-dev-user.sh

#!/usr/bin/env bash
# Usage: ./scripts/seed-dev-user.sh
# Requires: curl, jq, running backend on :8080

API="http://localhost:8080/api/v1"

echo "→ Creating org + admin user…"
RESULT=$(curl -s -X POST "$API/auth/register" \
  -H 'Content-Type: application/json' \
  -d '{"orgName":"Dev Org","orgSlug":"dev-org",
       "adminEmail":"dev@example.com","adminDisplayName":"Dev Admin"}')

echo "$RESULT" | jq .

echo ""
echo "✓ User created. Now open http://localhost:5173/login"
echo "  Enter: dev@example.com"
echo "  You will be prompted to register a passkey — do this once."
echo "  After that you can log in with your passkey anytime."

Make it executable: chmod +x scripts/seed-dev-user.sh

Problem: /login/begin requires the user to already have a registered credential. On first run, dev@example.com has no passkey yet.

Solution: after seed-dev-user.sh creates the user, redirect to /setup pre-filled so the developer completes passkey registration there — or add a special /register-passkey page that lets an existing user (identified by email) register their first passkey. The POST /register/begin endpoint you're adding already supports this: it works for any existing user regardless of whether they have credentials. Route: any logged-in user can also visit this page to add a passkey.
